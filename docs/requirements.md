# Технические требования

## 1. Назначение

Cloud Phone Bridge является сервисом-оркестратором между внешними системами автоматизации и API поставщиков облачных телефонов. Целевая нагрузка первой версии: не менее 100 одновременно зарегистрированных устройств с возможностью дальнейшего горизонтального масштабирования.

## 2. Основные сущности

### Phone

- `internal_id`: стабильный UUID внутри Bridge;
- `vendor`: код провайдера;
- `vendor_id`: идентификатор устройства у провайдера;
- `group_id`: логическая группа;
- `tags`: произвольные метки;
- `lifecycle_status`: `creating | stopped | starting | running | stopping | deleting | deleted | error`;
- `adb_status`: `unknown | connecting | online | offline | unauthorized | error`;
- `last_seen_at`, `created_at`, `updated_at`.

### Job

Асинхронная массовая операция: `queued | running | partially_succeeded | succeeded | failed | cancelled`. Job содержит результаты по каждому телефону и не считается полностью успешным при наличии ошибок отдельных элементов.

### ConnectionInfo

Краткоживущие данные подключения: IP/host, port, ticket/session token, срок действия и поддерживаемый протокол. Секретные поля маскируются в логах.

## 3. Функциональные требования

### 3.1 Lifecycle

Сервис должен поддерживать массовое создание, запуск, остановку и удаление устройств. Входной batch валидируется до постановки в очередь; некорректные элементы возвращаются отдельно и не блокируют допустимые элементы, если запрос допускает partial processing.

### 3.2 Connection info

`POST /phones/connection-info` принимает до 100 `phone_ids`, выбирает нужный адаптер, получает актуальные параметры подключения и возвращает данные по каждому устройству. Если данные генерируются долго, endpoint может вернуть `202` с `job_id`.

### 3.3 Приложения

Поддерживаются два режима установки:

- vendor marketplace: `app_id` и `version_id` передаются в API провайдера;
- custom APK: файл берется из доверенного object storage, проверяется checksum и устанавливается через ADB.

Произвольные локальные пути и URL из недоверенных источников запрещены.

### 3.4 Группы и теги

Сервис должен создавать группы, добавлять/удалять устройства из групп, назначать и снимать теги, а также фильтровать телефоны по `vendor`, `group_id`, статусам и тегам.

### 3.5 ADB

ADB Manager должен поддерживать connect/disconnect, install, push и выполнение разрешенного набора команд. Каждая операция имеет timeout, ограничение размера вывода и аудит. Долгие операции выполняются как Job.

## 4. Надежность

- идемпотентность всех изменяющих batch-запросов;
- очередь с повторными попытками и exponential backoff + jitter;
- отдельный rate limiter и circuit breaker на провайдера;
- chunking по фактическим лимитам vendor API;
- dead-letter queue для исчерпавших попытки заданий;
- блокировка конфликтующих команд на одном устройстве;
- восстановление незавершенных jobs после рестарта сервиса;
- graceful shutdown воркеров.

## 5. Безопасность

- Bearer/OAuth2 или подписанные access keys;
- RBAC минимум с ролями `viewer`, `operator`, `admin`;
- шифрование vendor credentials и connection tickets;
- запрет секретов в логах, traces и сообщениях ошибок;
- аудит изменяющих операций;
- сетевой allowlist для ADB endpoints;
- ограниченный набор ADB-команд вместо неограниченного shell по умолчанию.

## 6. Наблюдаемость

Метрики: размер очереди, latency, success/error rate, 429, retries, active ADB sessions, offline devices и длительность batch jobs. Логи должны содержать `request_id`, `job_id`, `phone_id`, `vendor`, но не секреты.

## 7. Критерии приемки MVP

1. Batch start/stop для 100 устройств не перегружает API провайдера.
2. Повтор запроса с тем же idempotency key возвращает исходный job.
3. Ошибка одного устройства не теряет результаты остальных 99.
4. Ответ 429 приводит к отложенному retry с учетом `Retry-After`.
5. Зависшая ADB-сессия завершается по timeout и помечает устройство `offline`.
6. Все операции доступны через документированный OpenAPI-контракт.

## 8. Открытые вопросы

- провайдер и API первой интеграции;
- реальные batch/rate limits;
- срок жизни connection ticket;
- способ доставки APK и максимальный размер;
- допустимый набор ADB-команд;
- требования к SLA, RPO/RTO и региону хранения данных;
- предпочитаемый стек и инфраструктура развертывания.
